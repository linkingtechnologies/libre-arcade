# The software archaeology behind Asteroids Infinity

This is Asteroids Infinity's own recovery story. For the philosophy shared by every game in this collection (why the reasoning is preserved and not only the artifact, why verification runs against executable originals rather than screenshots, why an unresolved question is reported as *unknown* rather than *impossible*) see [`../SOFTWARE_ARCHAEOLOGY.md`](../SOFTWARE_ARCHAEOLOGY.md).

The game arrives with a long audit trail of twelve milestones, condensed into [`specs/AUDIT.md`](specs/AUDIT.md), the original Python file ([`reference/`](reference/)) and the fixtures the tests replay. This file does not repeat them. It picks out what makes this specimen unusual and what integration into the collection checked again.

## One file, one author, one idea

The original is a single Python 2 script of 1012 lines that imports Pygame and nothing else. Ben Whittaker registered the project on SourceForge in June 2009 and its own summary is a list of four features, the first of which is the one worth preserving: "Nifty elastic viewpoint (viewpoint is loosely attached to the ship)". The second is "Upholds Newtons 1st law".

Those two sentences describe the whole design. The world is 700 by 540 units and the view is 640 by 480, so the camera has room to lag. Each frame it measures where the ship has got to, eases its own velocity toward the ship's by a factor that grows as the gap widens, then eases its position by `(1 - 0.1^dt)`. The ship, meanwhile, never stops: thrust adds velocity and nothing subtracts it. The result is that the screen swings behind you when you accelerate and settles when you coast, and that is the feel a port has to get right or there is no point porting it.

## What the source tells you that a screenshot cannot

Line 284 constructs an asteroid's spin:

```python
self.spin = random.uniform(math.pi * -2, math.pi * -2)
```

Both bounds are the same number, so the draw is a coin toss with one face: every asteroid in every game turns at exactly -2π. Almost certainly one of those signs was meant to be positive. The port keeps the value, and it still performs the draw, because removing the call would shift every later random number by one position and the recorded oracle would stop matching.

The scoring function has a quieter quirk of the same kind. `raise_score` only adds points when the attacker is the ship, or a bullet the ship fired, or nobody at all. A flying saucer that happens to shoot an asteroid earns you nothing, and the code says so in three explicit branches rather than one condition.

The collision sweep brings each pair of objects within half a world of each other before measuring the distance, so wraparound collisions work; but `Obj.update` wraps a position only once per axis, so an object travelling further than the world is wide in a single frame is not brought back. Both behaviors are in the port, and neither is a decision anyone would make twice.

## Running the original again, in pieces

Python 2 and Pygame were not available for this integration, and the audit that produced the port says the same about itself: no native session was ever run. What can be run is the code that does not need a display.

Two harnesses do exactly that. One extracts `Asteroid.__init__`, `Obj.update` and the wave-spawning statement straight out of the preserved file, executes them under Python 3 with a stub that provides only what Pygame's sprite groups were providing, and records every call to the random generator along with its bounds. The other executes the four functions that read and write `controls.txt` and `highscores.txt` and compares the bytes they produce with the JavaScript that reads the same files.

Both were re-run during integration. The asteroid fixture came out byte for byte identical to the one the tests already carried, which is the point: it shows the recorded oracle really is the original code's output and not a transcription of it. The file oracle passed too, after the harness was pinned to write LF line endings, because Python on Windows had been translating them and the comparison is a byte comparison.

## What is honestly missing

The original archive also contained a font, Vector Battle, and a set of WAV effects. Neither is here. The audit could not establish who may redistribute them, so it kept them out of the public package and said so, and this integration did not overturn that. The seven sounds you can turn on in the browser are square, sawtooth, triangle and sine sweeps generated by Web Audio, listed with their frequencies in `public/src/sound.js`. They are not a reconstruction of anything, and the Credits screen says as much before you ask.

The random number generator is missing in a subtler way. The port makes the same draws in the same order, but through `Math.random`, so a seed in the original and a seed here do not produce the same game. Tests that need exact numbers replay a recorded tape instead of pretending otherwise.

## What integration changed

The package arrived with the page at its own root (`index.html`, `style.css`, `src/`). The collection requires `public/index.html`, so those three moved into `public/` and the tests were repointed at them: path changes only, no assertion touched. It gained the collection's scripts (`dev`, `build`, `start`, `test`, `lint`, `check`), a `serve.mjs`, an ESLint config, the GoatCounter snippet and a "Play here" link.

Lint found one thing worth having: `savedLocal` was defined twice inside the same string table, in both languages. Both copies carried the same text, so nothing was ever wrong on screen, and the repeat is gone. A handful of unused locals in the test files went with it. The Python tests also read UTF-8 sources without naming the encoding, which fails on a Windows console; they now name it. The game's own logic was not touched, and the 113 Node tests pass unchanged.
