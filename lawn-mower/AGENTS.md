# AGENTS.md

- Licence of the original: **Public Domain**, in the author's words, in `game.asm` and `famitone.asm` (see `THIRD_PARTY_NOTICES.md` and `reference/source-v1.12/SOURCE.md`). The code written for this port is **GPL-3.0-or-later**, the collection's. The manual and the label of the competition archive have wording that could not be read, and are not kept. If the licence of the port is ever changed, change `package.json`, `README.md`, `THIRD_PARTY_NOTICES.md` and `PROVENANCE.md` together.
- `reference/` is frozen and byte-exact (`.gitattributes` turns line-ending normalisation off for the sources and the ROM). Never reformat or add to it: `test/reference.test.js` fails when a kept file changes. The zips, the editor program, the tracker projects, the manual and the label are deliberately not kept (`SOURCE.md` of each folder says why).
- **There are two versions and the port follows one of them.** `reference/competition/Lawn_Mower.nes` is the author's executable of 30 May 2011 (v1.1); `reference/source-v1.12/` is the source of 1 July 2011, and `reference/release-v1.12/Lawn_Mower.nes` is the author's own build of it (from the Internet Archive's zip). They differ in one thing that the game does: in the no-control path of `checkPad` (the level is cleared or the tank is empty) v1.1 clears the requested direction and v1.12 does not, so with v1.12 a moving mower starts into the next tile, at most 14 sixteenths of a pixel, before the end of the level takes over, where v1.1 stops it at the edge of its tile (`test/kernel.test.js` measures it). The port follows **v1.12** (`checkPadClearsDirection: false` in `kernel.js`, the default); the oracle runs the competition ROM with `true`, and the author's v1.12 ROM and the assembled v1.12 source with `false`, and all three agree to the byte. The one exception is the black screen while the fifth lawn is loaded, which the author's v1.12 ROM keeps for 10 NMIs on some entries (and 9 on others) where the port's table (`LEVEL_SETUP_FRAMES`) says 9; the oracle lets the port follow the ROM's length for that program (`follow`) and `test/oracle-release-v1.12.test.js` allows only that one to differ. Do not "fix" the table to 10 for lawn 5: the other two programs take 9 (`PROVENANCE.md`, "Open points"). To make the page follow the competition ROM instead, pass `checkPadClearsDirection: true` in `app.js`.
- **The oracle is the specification.** The ROM is run on `tools/nes-machine.mjs`, and `tools/lockstep.mjs` compares, at every NMI, the game's variables, the picture unit's memories (nametables, palette, sprites), the 11 bytes the sound player hands to the sound chip, and (with `tools/oracle.mjs`) the picture itself. `npm test` runs short versions with the three programs; `npm run test:live` runs long ones (about an hour and a half; start the programs in separate terminals with `--flavour v1.1`, `--flavour v1.12` and `--flavour v1.12-release`). After any change to `public/src/` run at least `npm test`; after a change to `display.js`, `ppu.js` or the sprite and tile code, read the picture differences it names (`tools/oracle.mjs` returns the frame, the kind of screen and the lines). Do not "improve" a rule, a number or a quirk: if the oracle says the port is wrong, the port is wrong.
- Things that look like bugs and are the original's (the oracle shows each): a skipped NMI that runs the game anyway when `fuelUpdateTime` goes looking for a place for the next can (it leaves X not zero, and X is where the loop keeps "this NMI is processed"); a START held on from the title into the first read of the pad in the level not counting as a new press (the previous read is the title's); START together with a newly pressed direction not un-pausing (the original compares the whole byte); the mower's left-edge sprites wrapping to the right edge; the message tiles being redrawn on rows 5 to 7, not 7 to 9, while it waits; the title's cheat buffer restarting with each showing of the title while the cheat itself stays on. `kernel.js` carries the reasons in comments.
- The kernel is a transcription of `game.asm`, routine by routine (`specs/port-map.md` lists them). It keeps the original's variables in the original's units (the 12:4 fixed-point position, the frame counters, `GAME_DELAY` used for several things) so that they can be compared with the ROM's memory; do not rename them for taste. The page-level parts (`app.js`: keys, touch, the loop, the panel, the language) are new code and are not compared with the ROM.
- The page presses START for ten steps, not one: the original reads the pad in only some of its loops, and sees a button as pressed when it was not down at its previous read, so a press shorter than the gap between two reads can be lost. `START_HOLD_STEPS` in `app.js` is the only place the page departs from the pad's behaviour, and it is a courtesy, not a rule of the game.
- The **cheat** of the original (the title's code RIGHT, UP, LEFT, LEFT, then SELECT skips levels) is in the kernel and the oracle uses it to reach the final screen. The page maps SELECT to Backspace and Shift and says nothing about it in the panel; the README does.
- Player-visible text carries no development vocabulary (`test/page.test.js` checks the shell; the panel's text is in `app.js`). The notes for developers are in the documents of the repository, not in the page.
- `tools/assemble.mjs` assembles the v1.12 source for the oracle. It is **not** the author's binary and must never be described as one: the author's own v1.12 ROM differs from what it builds in 7,013 program bytes (`reference/source-v1.12/SOURCE.md`, `reference/release-v1.12/SOURCE.md`). It is checked against two recorded hashes in `test/assemble.test.js`. (Lan Master's `tools/assemble.mjs`, with the zero-page rule of NESASM that this one lacks, assembles the same source into the author's v1.12 ROM byte for byte, checked on 18 October 2026; this folder's assembler and the oracle's "assembled" program have not been moved to it, see `PROVENANCE.md`.)
- `tools/static-translation/` is a bounded experiment (two routines translated to C and compared with the kernel; see its README). It needs Python 3 and gcc, is not run by `npm test`, and must not be described as a recompilation of the game or as NESRecomp. Its `results/` are reproducible byte for byte: if the kernel's stone rule changes, run it again and say why they changed.
- `public/src/famitone-data.js` and `levels-data.js` are data, not code: do not edit them by hand. `test/famitone-data.test.js` and `test/rom-data.test.js` rebuild them from the preserved sources and the ROM.
- The game advances on a `requestAnimationFrame` clock (one step per 1/60.0988 s, as many as are due), so it does not advance in a hidden tab. To try the page in a script, run it in a window that is shown (headless Chrome with a window works), and hold a key for at least one step (about 17 ms).
- The page layout was measured in a real browser at 320 by 568, 360 by 640, 390 by 844, 568 by 320, 812 by 375, 1024 by 600, 1280 by 800, 700 by 700, 500 by 420, 900 by 700, 800 by 640, 600 by 700 and 1100 by 800, in English and in Italian, with the information panel open: no scroll, a canvas of 256 by 240 proportions, every control inside the window, and the three option buttons overlapping neither the status bar (the picture's lines 14 to 34) nor the touch controls. Do the same after touching the CSS of `public/index.html`: the buttons shrink with the picture when the window is nearly square, go above it in a tall window and beside it in a wide one.
- `docs/development/` holds the restoration package's own notes with its milestone labels and old paths. Leave them as history; the facts of this integration are in `PROVENANCE.md`, `specs/port-map.md` and `CHANGELOG.md`.
