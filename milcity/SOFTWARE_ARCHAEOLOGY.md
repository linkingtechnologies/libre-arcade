# The software archaeology behind MilCity

This is the recovery story of this one game. The philosophy shared by every game in the collection (preserve the reasoning and not just the artifact, verify by execution rather than resemblance, record provenance instead of erasing it) is in [`../SOFTWARE_ARCHAEOLOGY.md`](../SOFTWARE_ARCHAEOLOGY.md).

## A war game made of threads

MilCity - Blue Edition is a game for J2ME phones (CLDC 1.0, MIDP 2.0, a 320 by 240 screen) by Jérémy Walther, whose Java package, `fr.uha.ensisa.ir.walther.milcityblue`, is the only hint of where it was made. The README says what it is in three lines: "Build your own city, earn money and produce energy ... and construct weapons! And, like in a Battleship game, you can use these weapons against your opponents." It was published on SourceForge as a source archive and a jar, and the last version, 1.0.5, is dated 19 February 2011. The README's own changelog starts with a first release whose Bluetooth game did not work ("Bug: Cannot play with Bluetooth") and goes on through five more: Bluetooth, the way the winner is decided, the balance of the costs, the score to reach and the money to start with as options, and how shields show on a spy's picture.

The game has a core of about 4,500 lines of plain Java, which knows nothing about screens: a grid of 30 by 30 cells, nine kinds of building, six weapons, a player for the person and another for the computer, and a small system of commands that a player sends to the others. A second part, of about 1,400 lines, is the model and the views that draw the grid and read the keys. A third, of about 750 lines, is the Bluetooth.

What makes it hard to port is not its size but how it moves. There is no game loop with a step. Each player has a thread that does one pass at the moment it starts and again every second: it counts the energy, the acceleration that the houses give, the money, the shields and the buildings, and then asks whether it has lost or won, and the computer's thread plays its move. The engine has another thread that paints ten times a second. Everything the person does happens at an arbitrary moment between two passes, and everything that has a duration is stored as an instant and compared with `System.currentTimeMillis()`: how long a building takes, when a weapon can be fired again, when a shield ends, how long the city has been without energy. Nothing is seeded. Each of the ten walkers that draw the coastline gets a new `java.util.Random` from the clock, and so does every choice of the computer. And drawing is not innocent: the view that paints the grid also moves the explosions on a step and fades the radar, so the game depends on being painted.

## What the restoration package had

The folder of reference material that came with the game is a restoration package. It carried the source archive, the deployed jar, a JavaScript port with a page around it, a few dozen reports and tests. The port had been written from a reading of the source and was careful in many ways: it had the numbers, the build orders of the computer and the layout of the grid. Its tests, however, asserted what its authors had read in the source and that the port repeats itself under a seed, and a script checked that certain facts were present in the Java text. The package said so itself: its parity document calls the browser "source-parity certified" for the deterministic rules, says that it is not certified against a running J2ME session "because no J2ME emulator is available in this runtime", and that the computer's trajectories "cannot be byte-for-byte compared" with the original because it "repeatedly creates unseeded `java.util.Random()` instances from wall-clock state". Nothing had run the original, and the claim of parity was a claim about reading.

That is level 3 of the collection's verification hierarchy, and for a game whose behaviour comes from clocks and threads it is a weak one, because the facts that matter are not in a function but in the order in which things happen.

## The oracle

There is no browser for J2ME, but there is a Java here. The core, the model and the views of the original compile unmodified against stand-ins for the handset's API (which draw nothing). Running them is the harder part, because the original reads the real clock, sleeps in threads and draws numbers from a generator nobody seeds. The solution keeps the original's code exactly as the compiler wrote it and changes what it runs on: a class loader rewrites three names in the constant pools of the original's classes, `java/lang/Thread`, `java/lang/System` and `java/util/Random`, to stand-ins that live in virtual time. A cooperative scheduler runs one thread at a time, in the order of the instants at which they asked to wake; the person's actions are put at exact instants before the tasks that are due; the seeds the original asks for come from a sequence that the port can also be given.

The harness plays a scenario (the options, a seed, and what the person does in each tenth of a second) on the port and then on the original, and compares a checksum of the whole state after each tenth of a second: every cell of both cities, the buildings and their times, the shield list, the radar, the money, the energy, the ammunition, the score, the vibration, how many seeds the original had taken. When the two differ it asks for the whole state of that moment and names the first line that differs. 13 scenarios are recorded as a fixture so that `npm test` can run without Java. They are meant to reach the places where the game does something: building under attack, shields, nukes, the computer's four levels, a blackout, a game left in the middle.

## What it found

The unseeded generators, which the package had named as the obstacle, are the easy part: the oracle hands both sides the same seeds, in the order they are asked for. What it found was elsewhere, and the first difference was about time. The package moved the game in whole seconds and settled the accounts only from the first one; the original settles them at the moment the game starts and every second after it, and reads the clock at the moment the person acts. Then, one by one, with each fix, the next difference came into sight (`specs/port-map.md` lists all twelve):

- **The computer's choice of target.** When the computer fires, the original creates a second generator to choose the opponent, and draws from it until the result is not the computer itself. The package drew nothing, so every shot of the computer used up different numbers, and all its later choices (where to build, where to shoot) were different from the original's. In a game with one opponent, which is the only game the page offers, the choice itself looks like nothing at all; what it costs is the numbers it takes.
- **Who scores.** The score of a command goes to "the other player" of the one hit, and the commander applies it only to the local player. So the person scores for hitting the computer's city and nobody scores for hitting the person's. The package gave the computer points, and with enough hits it could win by score.
- **The coastline.** The ten walkers all take a step before the water is looked at again. The package stopped as soon as the target was reached, in the middle of a round, which shows only when the target is not a multiple of ten cells: the water at 45% or 55%.
- **The shield.** The original does not keep a list beside the grid. It stores a shielded cell as its type with the sign changed, so that the cell no longer looks like grass, and puts the type back at the first pass after the minute. Nothing can be built under a shield for that reason, and a building that finishes under one drops it. The port now does exactly this.
- **The picture changes the game.** A click used to repaint, and a repaint moves the explosions on a step.

Two faults of the oracle itself were found in the same way, by a disagreement that turned out to be the measuring instrument's: the engine's thread timed a picture with the real clock, and a check whose option was mistyped selected no scenario and reported success. A check that checks nothing now fails.

## The author's own classes

The oracle compiles the source here. That the author's own deployed jar would behave in the same way is not a given: a compiler of 2011 for an old class file format could have produced a different program from the same text. The jar of the archive was unzipped (its classes are of class file version 46) and given to the oracle in place of the ones compiled here. The port agreed with it in 39 scenarios, 22,680 seconds of game. The wider run on the classes compiled here (65 scenarios, 37,800 seconds, 7,308 actions of the person, 10,169 seeds taken by the original) agreed throughout as well.

## What stays open

The oracle covers the game and not the page. The menus, the panel, the mouse, the saving and the layout were driven in a browser and read. The original's cursor, which moves with the handset's keys, is not the page's, and the page is not compared with it. The pictures are drawn by the page from rectangles because the original's three (the tile sheet, the splash and the icon) carry names that credit two people, "Shiro" and "Koojoo", and nobody has established the terms under which they were given; but the page's splash draws the same two characters over the same word, and whether that is far enough from art of unknown licence is for someone with a view of the matter to say (`PROVENANCE.md`, open points). The source archive is the file SourceForge serves (it was downloaded and the SHA-256 is the same); the deployed jar was not compared with SourceForge's. And the Bluetooth game, the half of the first release that did not work, is not ported at all, on purpose.
