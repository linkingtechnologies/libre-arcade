# Port map

Original: `reference/5ud0ku-1.8/source/src/de/wintermute/sudoku/` (Java ME for CLDC 1.0 and MIDP 1.0, 32 files, about 10,500 lines). Port: `public/src/core/` (the model, the solvers, the generator, the move history and the save layout, as ES modules) and `public/src/workers/` (the Web Worker that runs the generator and the custom-puzzle solver). The drawing, the input, the dialogs and the languages are in `public/src/browser/` and `public/index.html`: new code, not a port.

## Verification level

Following the collection's verification hierarchy (root `AGENTS.md`), the engine is at **Level 1, an executable oracle**: the original source is compiled unmodified and run, and the port is compared with what it answers. The parts of the game that only exist in the phone's user interface (`SudokuUI`, `SudokuStateControl`, `SudokuMidlet`) cannot be run here and are at **Level 3, source-level review**; they are listed separately below.

- **How.** `test/java-oracle/de/wintermute/sudoku/Oracle.java` lives in the original's package (the methods it needs are `protected`) and drives the original classes only through their own methods. Ten classes are compiled from `reference/5ud0ku-1.8/source/` without change: `AbortableTask`, `BruteForceSolver`, `CreatorTask`, `Grid`, `GridCreator`, `GridSlot`, `GridSolver`, `MoveStack`, `Position`, `Solver`. Three small stand-ins replace the classes that exist only on a phone: `Dict` (returns the key it is given), `SudokuMidlet` (`CreatorTask` hands the finished grid to it; the stand-in runs the callback at once) and `SudokuStateControl` (`CreatorTask` asks it for two preferences: the number of Hard candidates, 3 as in the original, and the timeout, see below). No rule is written again in the harness.
- **The two random streams.** The original seeds its two `java.util.Random` objects (`GridCreator.random` for the layout and the removals, `Grid.random` for the final relabelling of the digits) from the clock. They are `private static final`, so the harness reseeds them by reflection with `setSeed`, and the port takes the same two seeds. Nothing else about the original is touched.
- **What the generator test runs.** `GEN <level> <creatorSeed> <digitSeed>` runs the original `CreatorTask.createGame()` itself: the unique-game attempts, the choice of the best of three Hard candidates by the original's `checkAndStoreGrid()` (deeper backtracking first, then fewer singles and given numbers, then fewer given numbers), `clearPencilMarks()` and the final `randomizeDigits()`. The answer carries the board, the solution, the numbers shown, the singles, the backtracking depth, the type, the solution count measured by the original `GridSolver`, and the bytes of the original `toByteArray()`.
- **What was compared**, with `tools/java-oracle.mjs`, every answer identical:
  - **500 Easy, 500 Normal and 300 Hard games**, seeded at random, plus the package's three (`creatorSeed` 1801, 1802 and 1803 with `digitSeed` 91801, 91802 and 91803).
  - **514 puzzles for the solver**, run the way the original `SolverTask` runs them (`setAllShownDigitsAsOriginal()`, `checkForRules()`, and, only if the rules hold, `BruteForceSolver`): the package's ten, then puzzles made from valid solutions with 22 to 80 given numbers, with one given changed, with two cells swapped, with almost no given numbers and the empty grid. 106 fail the rules check, 6 pass it and have no solution, 184 have one solution and 218 have two or more (the solver stops at the second).
  - **600 sequences of moves, 81,910 commands**, on a grid and a `MoveStack`: setting digits and candidate marks, `setupPossibleDigits()`, `intializePencilMarks()`, singles and hidden singles, conflicts, hiding, promoting, clearing, resetting for edit, cloning, the digit counts, the validity tests, and the save and reload through `toByteArray()` and `Grid(byte[])` with types holding non-ASCII characters, the NUL character and a character outside the basic plane. Every tenth sequence is a history of 100 to 139 moves taken all the way back and forward, so the ring buffer wraps, and another tenth fills the board with its solution and then spoils one digit, so that the finished-board tests answer both ways.
  - **10 random-number streams** of 1,000 values each, including a seed whose first value is `Integer.MIN_VALUE`.
  - **A save written by the original classes.** `test/fixtures/m3-java-save-normal.hex` is a save from the package's Java run of the original `Grid`. The original `Grid(byte[])` reads it, `toByteArray()` writes the same 291 bytes back, and the port agrees.
- **The package's own fixtures.** The three generated games and ten solver puzzles of `test/oracles.json` are what the original produces.
- **Coverage.** The recorded commands exercise 98 to 100% of the lines of the ported engine files and 91 to 100% of their branches (`node --experimental-test-coverage test/java-oracle.test.js`): `grid.js` 100% and 100%, `grid-creator.js` 99.4% and 94.6%, `grid-solver.js` 100% and 97.4%, `brute-force-solver.js` 98.3% and 93.8%, `move-stack.js`, `grid-slot.js`, `position.js` and `solver.js` 100%, `grid-codec.js` 100% and 96.8%, `java-random.js` 100% and 90.9%. The uncovered lines are a defensive `return` that no run reaches (a position already empty chosen for hiding) and the end of `possible()`.
- **Can the oracle see a fault?** A set of 26 deliberate faults was put one at a time into a copy of the port: a changed number of symmetries, a wrong mirror cell, a tie rule changed for Hard, a Hard candidate count of 2, a hidden single that misses a row of the box, `isSingle` returning the index, a ring of 101 slots, `stepBack()` returning the other position, conflicts listed in another order, a solver that also looks at the rows below, a wrong given flag and a little-endian length in the save, a random generator that loses its top bit or has a wrong multiplier, and `clone()` copying the elapsed time, the backtracking depth, the marks or the flag. 23 were caught. The 3 that were not change no result the harness can see: one lets the uniqueness search run on to a third solution before stopping (the verdict is the same), one revisits a cell after a removal (the same position is reached), one clears a candidate that the row and column rules had already cleared. This was done once during the integration; the script is not kept. An earlier version of the harness missed the `clone()` faults, which is why the `CLONE` and `SETBT` commands exist.
- **Other runtimes.** The same run, with the same commands, agrees on Java 8 (1.8.0_503) and on Java 21 (21.0.2), the source compiled for release 8.
- **Recorded and live.** `npm test` replays the recorded commands (`test/fixtures/java-oracle.json`, tied by SHA-256 to the ten original files, the four harness files, `test/oracles.json` and the real save) and needs no Java. `npm run test:live` runs the original again, compares line by line and stops at the first difference with the command and the commands before it; it needs a JDK (`JAVA` and `JAVAC` choose the tools). To record again: `node tools/java-oracle.mjs record`.

**Limits.**
- The sample is seeded and broad, not exhaustive. Every Hard game and every uniqueness check is the original's code, but 1,300 games are 1,300 games.
- The original's wall-clock limits are not reproduced. In the original, Hard generation stops after 15 seconds even with fewer than three candidates (`DEFAULT_MAX_CREATION_TIMEOUT`); the stand-in sets the limit so high that it never fires, because a clock would make the result depend on the machine. On a phone of 2006 the limit mattered; in the browser the three candidates take about 30 milliseconds.
- `AbortableTask` is the original's way of cancelling a search. The oracle never aborts one, and the port cancels by ending the Web Worker.
- Easy and Normal retry in the original, without a limit, until a unique grid is found, and Hard does the same until it has three. The port gives up after 200 tries and reports an error. In the oracle's seeds about half of the Easy and Normal games needed more than one try (up to 12), and Hard up to 12 failed tries before its three candidates, so the retry loop is exercised, and the port's limit is far away; no game came near it.
- In the original `Math.abs(Integer.MIN_VALUE)` stays negative, and a draw of exactly that value (one in 4.3 billion) would index outside a vector. The port reproduces the arithmetic (the stream check includes such a seed) but the board it would produce was not compared. In practice it does not happen.
- The oracle compares the model and the generator, not pixels or timing. The input, the drawing and the dialogs have no original to compare with.

## What the port changes, and why

Differences found by reading the original's user interface (Level 3), not by the oracle:

- **Finishing.** The original calls a board solved when it is full and `isValidSolution()` (`SudokuUI.checkSolution`). The restoration package compared the board with the stored answer, which is the same for a generated puzzle (one solution) but would not recognise a different valid completion of a puzzle you entered with several. Fixed here to follow the original, and checked in a browser (a one-given puzzle completed with another valid solution wins; a full board with one wrong digit does not).
- **Entering the digit that is already there.** In the original this clears the cell (`SudokuUI.numberPressed`), and a cell that shows a digit takes pen mode even if pencil mode was on. The package did neither; both are now reproduced in `GameSession.inputDigit`, with the undo entry the original records.
- **Display Solution and Display Puzzle.** The original draws the stored answer in every cell and gives the digits the player entered a "correct" or "wrong" background (`SudokuUI.paintSlot`, `solutionViewCell` here); while it is shown no key or touch changes the board. The browser version adds a glyph (a tick or a cross) next to the colour, disables the digits and the tool buttons, and goes back with the menu or Esc. The view is not saved.
- **Reset Game.** The original clears the digits, the pencil marks, the elapsed time and the history, and then starts the timer (`SudokuStateControl.resetGrid` and `commandAction`); `GameSession.reset` is that method. The original asks nothing; the browser version asks for a confirmation, and recalculates the marks if beginner mode is on.
- **Edit current game.** The original turns the game on the board into an editable puzzle, keeping the given numbers (`SudokuMidlet.editCurrentGame`, `Grid.resetForEdit`). `editableGrid` does it on a copy, so Cancel returns to the game as it was; solving the edited puzzle gives a custom game, as for a puzzle typed in.
- **Marks on the number pad.** The original greys a digit used nine times (`getDigitCounts`) or marks the digits that clash at the cursor (`getConflictingDigitsForPos`); the port does not (the first is ported and tested, the second is not ported). Not changed.

Features of the phone application that the browser version still does not have: the menu commands that calculate, show, hide and clear the pencil marks (beginner mode and the pencil mode remain), the colour preferences, the quick-save key, the pointer-control mode of phones with a touch screen, and the German, Hungarian, Polish and Slovak texts. The browser version has English and Italian.

New in the browser version: responsive layout, number pad, keyboard and touch input, named saves in `localStorage` with a list, automatic saving, "erase local data", accessible labels, and the puzzle work in a Web Worker so that the page never freezes (the package's measurements in `docs/development/performance.md`).

Not reproduced because it is a defect of the phone user interface: the 128×128 pixel layout whose digit hit boxes overlapped the smiley and pencil controls (a statement of the package that could not be checked here, see `PROVENANCE.md`).
